# ADR-008：服务端自动挑空闲端口 + 扩展端自动发现服务端口（含身份校验）

## Status
Accepted（2026-10-07）

## Background
扩展写入 = 本机服务 `POST /api/apply`，默认端口 8788（`applytracker.py:6717`）。
端口可能变（8788 被占、用户 `--port` 改）。
`background.js:5-15` 已从 `chrome.storage.local` 读 `at_port`（默认 8788）——**只是「知道一个存好的端口」，不会发现**。
`popup.js:3` 还把看板地址写死成 `http://127.0.0.1:8788/`。

产品硬约束（PM）：**全程不需要打开命令行、不需要输入任何命令**。
据此两条约束同时成立：
- 「连不上就让用户去查端口再手填」不可接受 —— 那只是把放弃点从服务端搬到扩展端；
- **「端口被占就提示 `--port N+1`」也不可接受** —— 同学没有命令行，提示等于走不通。
  而扩展端既然已能自动发现（见下），「服务端必须固定 8788」这个前提就不成立了。

## Decision
**锁定（两侧对称，范围一致 = 8788/8789/8790/8791）：**
- **服务端**：启动时若默认端口被占，**自动在 8788–8791 内依次挑第一个空闲端口**，并在黑窗口**明确打印**实际端口（**不静默**）；四个端口全被占才报错让用户处理。
- **扩展端**：连不上当前端口时，在同一范围内自动探测，命中即写回 `at_port`；每个候选必须过身份校验；全失败才显示手填输入框兜底。

### 服务端选址
- **实际落点 = `start.command` / `start.bat`（已实现，团队裁决口径）**：探测用一段 Python 一行
  （`socket.connect_ex(("127.0.0.1", p))`，0.3s 超时；连不上=空闲）判空闲，取 8788–8791 第一个空闲端口，
  再 `applytracker.py --serve --port N`；四端口全占 → 中文报错并停住；落在非默认端口时**明确打印**
  「默认端口 8788 被占，服务改跑在 N，浏览器扩展会自动找到它」。用 Python 一行做探测，规避了
  「shell 测端口不可靠」的老问题（两侧脚本都用 `%PY% -c` / `"${PY}" -`）。两侧的「已在跑」前置探测也在同范围扫 8788–8791。
- **显式 `--port` 优先**：脚本挑到端口后明确传 `--port N`；用户自己传的端口同样被尊重。
- **兜底缺口已关闭（v0.30.0 落地，见下方「2026-10-08 补充」）**：原先 `serve()` 自身**没有**挑端口逻辑，
  所以**绕过 start 脚本的启动路径**在 8788 被占时仍走旧的硬失败「端口 8788 起不来…换端口：--port 8789」——
  - `开机自启.command:140-144` 写的 LaunchAgent `ProgramArguments = [..., applytracker.py, --serve]`（无 `--port`、无挑端口）；
  - 用户直接在终端跑 `python3 applytracker.py --serve`。

### 2026-10-08 补充：`serve()` 内补 `pick_port`（缺口关闭）
裁定：**补，且口径比原建议更宽 —— 不区分「是不是显式传了 `--port`」**。

- 落点：`pick_port()`（`applytracker.py:8577-8601`）+ `serve()` 内 `pick_port("127.0.0.1", preferred)`（`:8627`）。
- **不区分显式 `--port`**：原建议是「仅当未显式给 `--port` 时启用」。改成一律启用——显式指的端口被占也一样让。
  少一个分支，两条绕过脚本的路径（LaunchAgent `--serve` / 直接 `--serve`）自然都对，不用再同步改 `开机自启.command`。
- **唯一例外**：`--port` 本身超出 8788–8791（如 `--port 9000`）时只在它身上试一次，不漂到 9001
  —— 人既然手点了那个端口，就按那个端口办。区间内全占满 → 抛中文 `OSError`，`serve()` 翻成人话后 `return 1`。
- 实现方式：**每试一个端口就真建一次 server**（`ThreadingServer((host, p), Handler)`），建成功即占用。
  不采用「先探一下、再 bind」—— 探完关掉再 bind 中间有条缝，别的进程正好挤进来就又炸了。
- 自检（4 条，见 `applytracker.py:10679-10712`）：① 区间常量与 `start.command` 的 BASE/LAST 逐字对账；
  ② `pick_port` 存在且起不来时是抛错（源码级）；③ **真占住一个端口**后确实往上让；④ 区间只给一个且被占 → 抛 `OSError`。

### 探测流程（`background.js`）
1. 先用 `at_port`（默认 8788）试探 `/api/health`；通 → 直接用，不探测。
2. 不通 → 依次试 `8788, 8789, 8790, 8791`（跳过当前 at_port），每个：
   - `GET http://127.0.0.1:<port>/api/health`，**单端口超时 800ms**；
   - 仅当 HTTP 200 且响应体 JSON 满足 **`app == "applytracker"` 且有 `version`** 才认（`applytracker.py:6700` 的返回）；
   - 非 200 / 超时 / 非 JSON / 身份不符 → **跳过该端口**，继续下一个。
3. 命中 → 写回 `at_port`，重置探测节流（避免每次请求都探）。并在 `popup` 显示「已连接端口 N」。
4. 全失败 → `popup` 显示「服务端口」输入框兜底（写回 `at_port`），并提示「先双击 start 脚本把服务起起来」。

### 关键约束
- **必须在 background service worker 里发**探测请求：其 Origin 是 `chrome-extension://`，过 ADR-004 的 `_origin_ok()`；
  从 content script 发会带页面的 Origin，被 403。
- **必须是 GET、且目标是只读的 `/api/health`**：探测不能产生任何写副作用。
- **`manifest.json:7` 无需改**：`host_permissions` = `http://127.0.0.1/*`（host 级、不带端口）→ 覆盖任意端口；
  且该权限使响应可读，**不依赖 ACAO**（ADR-004 删掉 `*` 后探测照样能读响应）。
- **节流**：探测只在「当前端口失败」时触发，成功后写回 `at_port`；不在每次业务请求前探测。

## 成本评估（team-lead 要求）
| 项 | 量级 |
|----|------|
| 触发频率 | 仅在当前端口失败时一次（正常使用为 0） |
| 单端口超时 | 800ms（不是 background.js 现有业务请求的 6000ms） |
| 最坏耗时 | 4 个端口 × 800ms ≈ **3.2s**，一次性；命中后缓存，后续为 0 |
| 请求性质 | 只读 GET `/api/health`，无副作用、不消耗任何配额 |
| 代码量 | `background.js` 新增约 25 行；`popup.html` 加一个输入框 |
| 服务端选址 | `pick_port` 最多试 bind 4 次（微秒级）；只在启动一次，运行期零开销 |

## 误判风险评估（team-lead 要求）
| 场景 | 结果 | 结论 |
|------|------|------|
| 候选端口上是别的本机服务（如某个 dev server） | `/api/health` 非 JSON 或不含 `app=="applytracker"` | **跳过**，不误连 |
| 服务返回 JSON 但非 applytracker（如 `{"ok":true}`） | 缺 `app` 字段 → 身份不符 | **跳过** |
| 返回 403（服务拒绝该 Origin） | 非 200 | **跳过** |
| **端口上是另一个 applytracker 实例**（如作者 `tools/make-screenshots` 起的演示服务、或某人开了两个实例） | 身份校验**通过** → 连上错误实例 | **残余风险**（低）：单人单机；缓解见下 |
| 探测到的实例正在写同一个 `data/` 目录 | 两实例并发写被 ADR-005 的锁保护 | 不再丢数据，但语义上不应有两个实例 |

**残余风险（唯一一条）的缓解**：① 探测**按端口升序**、取最低者优先（真实例多为 8788）；
② `popup` 明确显示「已连接端口 N」，错连可见；③ README/安装说明写「**别同时开两个实例**」。
不做更强的机器指纹绑定（扩展读不到本地 `data/`，为此引入服务端握手 token 会违背本机/无账号的定位）。

## Consequences
- 正面：同学**既不需要处理端口占用、也不需要知道端口**（服务端自动挪、扩展自动找）；探测全程只读、可解释。
- 负面：`background.js` 多约 25 行 + `serve()` 多一个 `pick_port`；服务可能不总在 8788（扩展自动适配，用户无感）；
  `popup` 多一个「已连接端口」要显示。
- 回归/自检项：
  1. 8788 空闲 → 服务占 8788；`/api/health` 探测命中 8788；
  2. **8788 被占 → 服务自动用 8789 且黑窗口明确打印「端口 8788 被占，改用 8789」**；
  3. 8788 上放非 applytracker 服务、真服务在 8789 → 扩展必须连 8789（身份校验跳过 8788）；
  4. 8788–8791 全占 → `pick_port` 抛中文 `OSError`，`serve()` 翻成人话并退出（不静默、不卡死）；
     扩展走输入框兜底、不报错卡死；
  5. `--port 9000` 且 9000 被占 → **只在 9000 上试一次就报错**，不擅自漂到 9001；
  5. 显式 `--port 8790` 且 8790 被占 → **不自动跳**，按既有错误路径提示。
