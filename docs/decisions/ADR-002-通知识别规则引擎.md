# ADR-002：校招通知识别用可解释规则引擎，不用大模型

## Status
Accepted（2026-10-07）

## Background
邮箱通知要从「发件人 / 主题 / 正文」里认出五类通知（**测评、笔试、面试、资料补充、AI面**），
并抽取公司名与截止时间。用户（作者）原话级要求：**宁可不标，也不要标错** —— 她看到错标就不信这个工具。
硬约束：零第三方依赖、Python 3.9、**本机运行不得调用任何大模型**。

现成资产：`../qqmail-job-tracker/qqmail2table.py` 已有一套纯正则规则引擎（`TYPE_RULES` 等，见下），
但它只有 4 类（AI面/测评/Offer/状态更新），且把「笔试」并进「测评」、没有「资料补充」，
`AI面` 规则里含 `视频面试`（会误判）。需要在移植时**扩类 + 纠偏**。

## Decision
**锁定：纯规则引擎（关键词表 + 发件人域名 + 正则），移植并扩写 `qqmail2table.py` 的规则层，不引大模型。**

大模型方案排除理由：不可解释（给不出「命中哪条规则」）、不可复现（同一封邮件两次可能不同）、
引入网络依赖与隐私风险（要把邮件正文发出去），三者全部违反本项目的本机/离线/可审计定位。

### 1. 类别规则（扩到五类，顺序即优先级）

> 顺序即优先级：越具体越靠前。由 `classify`（`qqmail2table.py:327`）+ `narrow_types`（61）实现，移植后扩表。

```
资料补充  ["补充材料","补充资料","提交材料","上传材料","完善简历","资料审核",
          "资格审核","资格复审","补充信息","证件上传","信息确认","材料提交"]
AI面     ["ai面","ai 面","ai面试","ai 面试","智能面试","机器人面试","数字面试",
          "ai video interview","one-way interview","vi面"]
笔试     ["在线笔试","笔试邀请","笔试通知","笔试安排","参加笔试","笔试试卷",
          "written test","笔试"]                    ← 从原「测评」里拆出来
测评     ["在线测评","测评邀请","能力测评","综合测评","人才测评","性格测试",
          "认知能力","assessment","online test"]     ← 不再含「笔试」
面试     ["面试邀请","面试通知","面试安排","邀请.*面试","初面","复面","一面","二面",
          "终面","群面","无领导","interview","面邀"]
```

**纠偏（相对 `qqmail2table.py:47`）**：
- 从 `AI面` 移除 `视频面试`。「视频面试」可能是真人视频面 → 归 `面试` 且降置信（见下）。
- 「笔试」从 `测评` 独立成类，因为看板的面试阶梯（`applytracker.py:2600 INTERVIEW_ORDER`）里
  `测评` 与 `笔试` 本就是两个节点，混为一类会让进度条认错环节。
- 否定类（**不进通知表**）：`感谢信`/`未通过`/`遗憾地通知`/`已挂`/`不再推进`/`宣讲会`/`空中宣讲`/`退订`/`招聘推送`。
  这类命中即写入 `data/mail_skipped.jsonl` 备查，**不冒充五类里的任何一类**。

### 2. 置信度：分层，弱信号只进待确认区

- **强信号**：主题命中类别词（`+2`）或发件人域名在白名单（`+1`）。
- **弱信号**：仅正文命中（`+1`，且需 ≥2 个不同关键词才算）。
- 得分最高者为主类型；**最高分 ≤ 1（只有弱信号）→ 类型留空**（数据里是空串，不写「待确认」字样）。
- **并列（两个类型同分）→ 一律留空**，不猜。

⚠️ **2026-10-08 修订（原决策：不进通知表，单独落 `data/mail_review.csv`）**：
这条被用户否掉了 —— 拿到发行版的人根本不会想起来去翻一个 CSV，类型认不出的邮件就等于石沉大海。
现改为：**只要公司名认得出来，就照样作为正常一行进通知表**，类型留空 + 页面打「待确认」角标，
点一下能选类型（`POST /api/notice-type`）。只有**公司名认不出**的才走 `mail_unmatched.csv`。
`mail_review.csv` 自此废弃。词表也同期放宽：用户要求把裸「测评」加回 `测评` 类
（原来只认「在线测评 / 测评邀请」这类组合词），并明确接受代价 —— 已结束的测评邮件也会被标出来，
因此**不许**再加否定词去筛。

`narrow_types` 的收缩规则保留（`qqmail2table.py:61`）：命中 `AI面` 则丢掉 `面试`；命中具体环节则丢掉否定类。

### 3. 抽取规则（直接移植）

- **截止时间**：`extract_deadline`（`qqmail2table.py:401`）三层——绝对日期（`DATE_PATTERNS`，80）+
  上下文词加权（`DEADLINE_HINTS`，70）/降权（`DEADLINE_NEGATIVE_HINTS`，76）→ 相对表述（`extract_relative_deadline`，371，`N 天内/小时内/工作日内`）→ `default_deadline_days` 兜底（默认 0 = 不兜底）。
  **抽不到就留空**（看板对空值已有 `9999` 沉底逻辑），绝不按邮件时间硬推一个假的。
- **岗位名**：`extract_position`（493）。**抽不到留空**，不猜。

## Consequences
- 正面：每条判定都能说出「命中哪条规则、命中哪个词、发件人是谁」——可解释、可复现、可审计；
  离线、零依赖、无隐私外泄。
- 负面：规则永远追不全新模板 → 靠「待确认区 + 用户一次归类」补（见 ADR-003 公司匹配里的 `mail_aliases` 思路）。
- **可复现性落地**：每条识别结果把「命中依据」写进旁路文件 `data/notice_evidence.json`（键 = `applytracker.py:1352 notice_state_key` 算出的稳定键），
  **不改 notices.csv 的列**（`NOTICE_FIELDS` 维持在 `applytracker.py:1342`）。看板上一封通知可点开看「为什么标成这个类型」。
- 风险：调规则时若只加关键词不做负例，会把「测评通过后进入面试」这类同时命中的邮件标乱 →
  由「并列降级 + 主题优先 + 待确认区」三道拦截。
